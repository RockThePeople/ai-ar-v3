# 요청 (3090 → A5000) — `chunk_key` 검증이 아직 v3 범위(0–7)다

## 증상

계약 v4 로 올려 준 것 확인했다 — 생성물이 실제로 v4 다 (헤더 판본 바이트 4,
v4 클라이언트로 디코드 성공, 415청크). **그런데 청크 내려받기가 372/415 실패한다.**

```
GET /v2/assets/<id>/staging/<job>/chunks/10_10_0.cbin
→ 422 {"error_code":"INVALID_REQUEST","message":"chunk_key 형식이 아니다: '10_10_0'"}
```

받아진 43개는 **전부 인덱스가 7 이하**다. 8³ 격자의 유효 범위 그대로다.

## 원인

`CHUNK_GRID_RES` 가 8 → 16 이 되면서 청크 인덱스가 **0–15** 로 늘었는데,
`chunk_key` 검증 정규식이 아직 **한 자리(0–7)** 만 받는 것으로 보인다.

리포의 계약(`contract/python/deltacontract/uris.py`)은 세 자리 다 통과한다:

```
7_7_7      → OK
10_10_0    → OK
15_15_15   → OK
```

## 고칠 곳

`:8082` 쪽 `chunk_key` 검증을 리포 계약과 맞춰 달라. 리포의 `uris.py` 를 그대로
쓰는 것이 가장 안전하다 — 정규식을 손으로 다시 쓰면 또 갈라진다.

## 곁들여 — 헬스가 먼저 v4 라고 답했다

`/v2/trellis/health` 의 `contract` 블록은 이미 `contract_version 4 · chunk_size 4 ·
chunk_grid_res 16` 이다. 그런데 그 시점에도 생성물은 v3 였다 (W26 실측). 선언과
산출이 갈릴 수 있다는 뜻이라, 3090 쪽 가드는 **헬스 선언만 믿지 않고** 실제 바이트를
확인하는 쪽으로 가야 한다는 걸 배웠다 (D28 과 같은 논리).
