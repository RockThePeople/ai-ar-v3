# 실물 자산 — v4 격자 (`CHUNK_SIZE = 4`)

🔴 **Unity 화면이 큐브였던 원인이 여기 있었다.**

리포에는 지금까지 `tools/build_moto_patch.py` 가 `occupancy_to_mesh`(복셀당 큐브 +
FACE_INSET)로 만든 **합성본**만 있었다. A5000 TRELLIS 디코더가 낸 **실물 메시**는
3090 에만 있었고 리포에 없었다. 렌더러 문제가 아니라 **자산 문제**였다.

판별식과 실측 — 같은 자산, 같은 색, 같은 파이프라인:

| | 청크 | 면 | **면 법선이 축에 정렬된 비율** |
|---|---|---|---|
| 합성본 (`occupancy_to_mesh`) | 375 | 109,800 | **100.0%** ← 전부 큐브 면 |
| **실물 (이 디렉터리)** | 376 | 359,220 | **5.1%** |

109,800 = 9,150복셀 × 12삼각형. 큐브라는 뜻이 숫자에 그대로 있다.

## 앱에서 쓰는 법

`tools/build_lasso_apk.sh` 는 `$V3_CHUNK_DIR/parent` 를 읽는다. 기본값이 리포 밖
(`$REPO/../.inplace`)이라 합성본이 들어가고 있었다. **실물을 쓰려면:**

```bash
V3_CHUNK_DIR=$PWD/assets/moto-b tools/build_lasso_apk.sh
```

(기본값 변경은 앱 담당 판단이라 건드리지 않았다 — 필요하면 맥북이 한 줄 바꾸면 된다.)

## 어떻게 만들었나 — 기하를 새로 만들지 않았다

구 계약(v3) `.cbin` 의 정점·면·색을 **그대로** 읽어 v4 격자로 다시 나눴을 뿐이다.
자르는 자리만 바뀐다.

```bash
python3 tools/extract_v3_mesh.py <v3계약경로> <구청크디렉터리> mesh.npz
python3 tools/repartition_asset.py mesh.npz <출력> --slat handoff/lasso/<자산>.slat_coords.npy
```

⚠️ v4 디코더는 v3 바이트를 **거부한다** (`ChunkBinError: 계약 버전 불일치 file=3,
local=4`). 그게 D75 의 안전장치이고 옳게 동작하는 것이다. 그래서 계약을 고치지 않고
**D75 직전 커밋의 워크트리**를 만들어 옛 리더로 읽었다. 두 계약이 한 프로세스에서
만나지 않는다.

⚠️ `voxel_cells` 로는 **slat 좌표**를 넘겼다 (D28 정본). 표면 복셀화를 넘기면 청크별
`voxel_count` 가 정본과 어긋나는데 **예외는 안 난다.**

정점이 늘어난 것은 청크 경계에서 복제되기 때문이다 — 면 수가 같으므로 기하는 그대로다.

⚠️ 바이트 총계가 **줄었다** (moto-b 9,763,456 → 7,646,272 · dragon-c 11,573,456 →
9,062,024). 청크가 많아졌는데 작아진 것이라 직관과 반대다. 왕복 검증(면 수 동일 ·
IoU 1.000000)으로 손실이 아님은 확인했지만 **왜 줄었는지는 확인하지 않았다** —
청크가 작아 위치 양자화 범위가 좁아진 효과로 보이나 그건 추론이다.
